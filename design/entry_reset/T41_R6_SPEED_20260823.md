# Ticket 41 — can R6 be made faster losslessly

Answer: **not by compiler flags. That lever is now measured and exhausted.**
The remaining cost is the row calling back into Python for the families wave 2
did not port, so more speed means porting more families.

## What was tried, and what it bought

Flags before: `-std=c++20 -O2 -g -fPIC -shared -Wall -Wextra -Wpedantic -Werror
-ffp-contract=off`.

Tried `-O3 -march=native -fno-math-errno`, keeping `-ffp-contract=off` and
adding nothing that lets GCC reorder a floating-point reduction.

| Build | ms/row (wave 2 shipped) | Speedup vs oracle |
|---|---|---|
| `-O2` | 3.8616 | 1.851x |
| `-O3 -march=native -fno-math-errno` | 3.8385 | 1.841x |

The 0.6% is inside the run-to-run spread: the untouched Python oracle moved
7.1473 to 7.0668 in the same pair of runs, which is 1.1%. **No gain.**

Byte-identity held throughout — proven, not argued:
`disc_native_differential_o3_allstore300.json`, 5 of 5 store sessions PASS.

`-march=native` was then **removed anyway**. Zero measured gain does not justify
a binary that dies with SIGILL if the pod's CPU changes under it, and this pod
restarts. Final flags keep `-O3 -fno-math-errno`, re-proven byte-identical in
`disc_native_differential_o3_final_allstore300.json`, 5 of 5 PASS.

## The defect this uncovered, which was worth more than the flags

`qrdisc_source_manifest()` hashed the C++ sources and **not the compile flags**,
while that sha addresses the build directory. So raising `-O2` to `-O3` left the
cached `.so` at the same address, the next run silently loaded the OLD binary,
and any speed or byte-identity number taken from it would have been measuring
code that is no longer the code on disk.

The loader's own docstring says it exists to stop "an edited kernel plus a
cached .so" — it guarded sources and left the flags open. Fixed: the manifest
text now begins with a `FLAGS` line and the sha moves when a flag moves.
Red-first fixture
`test_qrdisc_state_marshal.test_manifest_sha_covers_the_compile_flags`, which
failed on the pre-fix code with the flags absent from the manifest text.

Every speed number in this document was taken after that fix, so each one came
from a binary built with the flags it claims.

## Where the time actually goes, and what would move it

Wave 2 ports eight families and assembles the row natively. Every family it did
NOT port still resolves through the delegation table back into Python, per row.
At 3.84 ms/row against the oracle's 7.07, roughly half the row is still Python.

So the honest ranking of remaining speed work:

1. **Port more families (a wave 3).** This is the only lever with real headroom
   left, and it is C++ work with a differential per family, exactly as waves 1
   and 2 were done. The ceiling is the oracle's 7.07 ms/row falling toward the
   native families' share.
2. **Cut rows, not time.** The corpus builds every scheduled snapshot; D-110
   already rules that only the four Delta-grid rows per series are needed, which
   is a far larger factor than any compiler setting and costs no fidelity.
3. Compiler flags. Done, measured, worth nothing.

Lever 2 is the one to take first: it is a scope constant in the corpus build,
not a port, and D-110 already authorises it.

## The lever that actually matters, quantified

`confirmation.training_offsets_seconds(300)` schedules **37 offsets per series**.
D-110 rules that the corpus needs only the four Delta-grid rows per series. That
is a **9.2x** cut in rows, and it costs no fidelity because the discarded rows
are ages the entry work never reads.

Against the same measured 3.8616 ms/row, 2,625 sessions, 13.6 cores:

| Rows built | s/session | CPU-hours | Wall |
|---|---|---|---|
| all 37 scheduled offsets | 84.9 | 61.9 | **4.55 h** |
| D-110's four-row grid | 9.2 | 6.7 | **0.49 h** |

**Half an hour for the whole 2022-2025H1 corpus**, against four and a half.

Put beside the flag experiment: `-O3 -march=native` bought 0.6%. The row rule
already on the books buys 89%. That is the entire lesson of this ticket, and it
is why the compiler was the wrong place to look.

Ranked, with the arithmetic each rests on:

1. **Apply D-110's four-row grid to the corpus build.** 9.2x, measured offsets,
   authorised law, no port required. Do this first.
2. **Port more families (wave 3).** About half the row is still Python at
   3.84 ms against the oracle's 7.07, so the ceiling here is under 2x, and it is
   real C++ work with a differential per family.
3. **Compiler flags.** Measured at 0.6%. Closed.
