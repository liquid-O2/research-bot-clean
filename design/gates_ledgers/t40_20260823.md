# Gates: ticket 40 — a C++ databento reader for the off-2021 corpus

Scope: D-109's speed option, named by the user. The 2022-2025H1 corpus is about
2,625 sessions, 4.5x the entire 2021 store, and nothing may launch without the
six-hour arithmetic. Measure the Python decode rate, measure what C++ buys, and
put both in front of the user before any corpus build starts.

Law: no scope cuts to fit the clock (D-109 amendment) — speed comes from faster
code. 2026 raw is sealed escrow. 2025H2 is sealed. The generator is frozen: this
ticket changes how bytes are READ, never what a candidate is.

- [x] C1: the Python decode rate is measured on real raw bytes, one full
        session, with the wall time and the event count receipted
  EVIDENCE: MEASURED today on real 2022 Silver bytes. Python (zstandard stream_reader across frames + databento_dbn.DBNDecoder): 690,748 records of session 20220106 in 0.11 s = 6,346,051 rec/s. The first attempt read 16 KB and 1 record because zstd's decompress() stops at the first frame; read_across_frames=True is required, and the wrong number was caught before it was quoted.

- [x] C2: the existing C++ build is identified — toolchain, how it is built, and
        whether a Databento decoder is already linked or must be added
  EVIDENCE: The C++ Databento reader ALREADY EXISTS and is built. vendor/databento-cpp is vendored; engine/cpp/qr_databento ships an MBP-1 adapter (include/qr_databento/adapter.hpp); artifacts/cache/cpp/release/bin carries 61 binaries including qr_futsess_decode and qr_futsess_assemble. Measured on the same 3 sessions: decode 0.19 s for 1,643,821 records on ONE worker (8,654,119 rec/s, 0.06 s/session), assemble 0.07 s (0.02 s/session). Both ran clean on 2022 bytes: 3 day receipts, 192 foreign dropped, 0 file failures.

- [x] C3: the full-window arithmetic is written from the measured rate, per
        D-109: sessions x per-session rate x the HARDWARE.md core budget, for
        both the full 2022-2025H1 window and the cheaper 2022-only first cut
  EVIDENCE: Substrate: 2,625 sessions x 0.08 s = about 3.5 min (measured today, C++). Builders: OptMem #92 records the discretionary builder at about 3 min/session native versus 21 min in Python - a remembered figure, NOT receipted here, and it must be re-measured before it is spent against. Under it: full window 2,625 x 3 min = 131 CPU-hours, about 9.6 h wall across HARDWARE.md's 13.6 cores, which is OVER the D-109 six-hour cap. 2022 alone (about 750 sessions) = 37.5 CPU-hours, about 2.8 h wall, which is UNDER it. In Python those become roughly 67 h and 19 h wall - both impossible.

- [x] C4: the speed option is priced, not asserted — what a C++ reader would
        change, on the measured split between decode and everything downstream
  EVIDENCE: PRICED, and it overturns the premise. C++ decode is 8.65M rec/s against Python's 6.35M - 1.4x, not orders of magnitude - and BOTH are free at this scale. The whole raw substrate for 2022-2025H1 (about 2,625 sessions) costs 0.08 s/session in C++, roughly 3.5 minutes total, versus about 4.8 minutes in Python. Decode is not the bottleneck and a new C++ reader would buy nothing, because the one that exists already runs the stage in minutes. The cost is entirely downstream of the substrate, in the discretionary/candidate/feature/teacher builders.
